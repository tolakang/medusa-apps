## 2. Password reset tokens: PASS

- Installed core-flows `dist/auth/workflows/generate-reset-password-token.js:8`: `RESET_PASSWORD_TOKEN_TTL_SECONDS = 15 * 60`. The token is a JWT with `jwtid` from `createPasswordResetTokenStep` (stored, single-use), `purpose: "reset"`.
- The custom `POST /store/customers/me/password-reset` reuses `generateResetPasswordTokenWorkflow`, so it gets the same lifetime.
- Reuse refused: `account-auth.spec.ts:90-113` ("The token works only once" → second update ≥ 400). Unknown email answers the same and sends nothing (`:115`).
- Reset links use `STOREFRONT_URL` / `MEDUSA_BACKEND_URL` from env, not request headers (`medusa-config.ts:197,240`).
- Email verification tokens: `randomBytes(32)` (`@medusajs/auth/dist/utils/verification-token.js:9`), TTL 900 s; unguessable.
- RISK-low: no test for the 15-minute expiry (core behaviour). The token stays in the reset page URL (`reset-password/index.tsx:16`); with the browser default referrer policy only the origin leaves the site.

## 3. Input validation & injection: PASS (2 low)

- Every custom body has a Zod schema in `middlewares.ts` (`PostAdminUploadLimit`, `PostCustomerPassword`, `PostWishlistItem`). Other `req.body` reads are guards that only check types (`auth-guards.ts:20,40,83`, `contact-validation.ts:44`) or the secret-gated Telegram webhook.
- Raw SQL: none (`git grep -nE "\.execute\(|\.raw\(|knex\.raw" -- ecommerce/backend/src` → only a comment in `captcha.ts`).
- XSS: no `dangerouslySetInnerHTML` in backend or storefront; order email template escapes every value (`modules/resend/templates.ts:23-44`, `escapeHtml`).
- Outgoing calls go only to fixed or env hosts: Resend, Telegram, PayWay (`PAYWAY_API_URL`), storefront revalidate (`STOREFRONT_URL`). No URL from the request.
- PayWay callback signature is verified with a constant-time compare (`modules/payway/service.ts:305-307`).
- Low: Zod strings have `.min()` but no `.max()` (e.g. `current_password`, `variant_id`); the body parser's size limit still bounds them.
- Low: uploads block SVG by type and extension (`api/upload-limits.ts:22-23`) and enforce a size limit; it's a blocklist, admin-only.

## 5. Rate limiting: FIX

Limited (`middlewares.ts`, `limitPerIp`, `AUTH_LIMITS` in `auth-guards.ts:153`): customer login 20/min, signup 10, reset-password 10, verification request 10, password change 10. CAPTCHA and `SHOPPER_IP_SECRET` are in the runbook (`DOKPLOY_STAGING.md:51,149,158`). Replicas = 1 (`DOKPLOY_STAGING.md:244`), so the in-memory limiter is valid.

Gaps:
- **`POST /auth/user/emailpass` (admin login) and `POST /auth/user/emailpass/reset-password`: no limit** → admin password guessing and reset-email flooding. (Admin MFA exists, `admin-mfa.spec.ts`, which reduces but doesn't remove the risk.) → E-A1.
- `POST /store/customers/me/password-reset`: no limit, but signed-in and only mails the customer's own address. Low.
- `POST /auth/verification/confirm`: no limit; codes are 32 random bytes, so guessing isn't feasible. OK.
- Before production: set `CAPTCHA_PROVIDER` (empty = off) or record the RISK.

## 6. Error handling & leaks: FIX (low)

- Core error handler returns `"An unknown error occurred."` for 5xx (`@medusajs/framework/dist/http/middlewares/error-handler.js:34,86`). Custom code throws `MedusaError` with user-facing text; no `err.stack` or `res.json(err)` anywhere.
- `NODE_ENV=production` in both Dockerfiles (`backend/Dockerfile:43`, `storefront/Dockerfile:62`); in production Medusa refuses to start without `JWT_SECRET`/`COOKIE_SECRET` (`framework/dist/config/config.js:50-51,81-91`).
- Storefront has `not-found.tsx` pages but **no `error.tsx` or `global-error.tsx`**, so a crash shows Next's bare default page. `next.config.js` doesn't set `poweredByHeader: false`, and Medusa/Express keeps `X-Powered-By: Express`. → E-A2.
